# Detailed Implementation Plan: Availability Management & Notifications

## Introduction
This document outlines the step-by-step plan to implement a system for specialists to manage their availability and for users to receive notifications about appointments.

---

##To fix in availability:

**Part 1: Availability System Enhancements**

**Phase 1.1: Flexible Appointment Durations**

1.  **Update `app/schemas/specialist.py`:**
    *   Add a new field `appointment_duration` (in minutes, e.g., `int = 30`) to the `Specialist` schema. This will allow each specialist to have a default appointment duration.
2.  **Update `app/routers/availability.py`:**
    *   In the `get_available_slots` function, instead of using a hardcoded `appointment_duration_minutes = 30`, fetch the `appointment_duration` from the specialist's profile.
    *   Provide a fallback to a default value (e.g., 30 minutes) if the specialist has not configured a specific duration.

**Phase 1.2: Appointment Types**

1.  **Create `app/schemas/appointment_type.py`:**
    *   `AppointmentTypeBase(BaseModel)`: Defines `name` (e.g., "Initial Consultation"), `duration` (in minutes), and `description`.
    *   `AppointmentTypeCreate(AppointmentTypeBase)`: Schema for creating a new appointment type.
    *   `AppointmentTypeOut(AppointmentTypeBase)`: Schema for returning an appointment type, including its ID.
2.  **Create `app/db/models/appointment_type.py`:**
    *   Implement `individual_serial` and `list_serial` functions for `appointment_types`.
3.  **Create `app/routers/appointment_types.py`:**
    *   Implement full CRUD endpoints for managing appointment types (`/appointment-types/`). This will allow specialists to create, view, update, and delete their own appointment types.
4.  **Update `app/schemas/appointment.py`:**
    *   Add an `appointment_type_id: str` field to the `Appointment` schema.
5.  **Update `app/routers/appointments.py`:**
    *   When creating an appointment, the `appointment_type_id` will be required.
    *   The duration of the appointment will be determined by the selected appointment type, overriding the specialist's default duration.

**Phase 1.3: Buffer Time Between Appointments**

1.  **Update `app/schemas/specialist.py`:**
    *   Add a `buffer_time` field (in minutes, e.g., `int = 10`) to the `Specialist` schema.
2.  **Update `app/routers/availability.py`:**
    *   In `get_available_slots`, after an appointment is booked, add the `buffer_time` to the end of the appointment to create a buffer before the next available slot.

**Phase 1.4: Enhanced Time-Off Management**

1.  **Create `app/schemas/time_off.py`:**
    *   `TimeOffBase(BaseModel)`: Defines `start_date`, `end_date`, and an optional `reason`.
    *   `TimeOffCreate(TimeOffBase)`: Schema for creating a new time-off entry.
    *   `TimeOffOut(TimeOffBase)`: Schema for returning a time-off entry, including its ID.
2.  **Create `app/db/models/time_off.py`:**
    *   Implement `individual_serial` and `list_serial` functions for `time_off`.
3.  **Create `app/routers/time_off.py`:**
    *   Implement CRUD endpoints for managing time off (`/time-off/`).
4.  **Update `app/routers/availability.py`:**
    *   In `get_available_slots`, in addition to checking for blocked slots, also check for time-off entries and filter out any slots that fall within a time-off period.

**Phase 1.5: Recurring Blocked Slots**

1.  **Update `app/schemas/availability.py`:**
    *   Add a `recurrence_rule` field to the `BlockedSlot` schema. This could be a string following a standard format like iCalendar's RRULE (e.g., `"FREQ=WEEKLY;BYDAY=MO"` for every Monday).
2.  **Update `app/routers/availability.py`:**
    *   In `get_available_slots`, when fetching blocked slots, also fetch recurring blocked slots.
    *   For each recurring blocked slot, calculate the occurrences that fall within the requested date range and treat them as regular blocked slots for filtering purposes.

**Phase 1.6: Robust Timezone Handling**

1.  **Standardize on UTC:**
    *   All `datetime` objects will be stored in the database in UTC.
2.  **Update `app/schemas`:**
    *   Ensure that all `datetime` fields in Pydantic models are timezone-aware.
3.  **Update `app/routers`:**
    *   When creating or updating any object with a `datetime` field, ensure that the `datetime` is converted to UTC before being stored in the database.
    *   When returning any object with a `datetime` field, the API can either return it in UTC (and let the client handle the conversion) or accept a `timezone` parameter to convert it to the user's local timezone.


## Part 2: Notifications (Real-Time with WebSockets)

### Phase 2.1: Database and Schema Definition
1.  **Create `app/schemas/notification.py`:**
    *   `NotificationBase(BaseModel)`: Defines the core fields for a notification (`user_id`, `message`, `read`).
    *   `NotificationCreate(NotificationBase)`: Schema for creating a new notification.
    *   `NotificationOut(NotificationBase)`: Schema for returning a notification, including its ID and creation timestamp.

2.  **Create `app/db/models/notification.py`:**
    *   Implement `individual_serial` and `list_serial` functions to serialize notification data from MongoDB.

3.  **Database Collection:**
    *   A new collection named `notifications` will be created to store all user notifications.

### Phase 2.2: Real-Time WebSocket Communication
1.  **Create `app/utils/websockets.py`:**
    *   This file will contain a `ConnectionManager` class.
    *   The manager will handle active WebSocket connections, maintaining a mapping of `user_id` to their active connection to enable real-time messaging.

2.  **Update `app/routers/notifications.py`:**
    *   A WebSocket endpoint will be added: `WS /ws`.
    *   When a user connects, this endpoint will register their connection with the `ConnectionManager`.
    *   It will handle disconnection logic to gracefully remove users from the manager.

3.  **Update `app/main.py`:**
    *   Import and include the new notifications router.

### Phase 2.3: Notification Utility
1.  **Create `app/utils/notifications.py`:**
    *   This file will contain a core helper function: `create_and_send_notification(user_id: str, message: str)`.
    *   This function will:
        1.  Create the notification and save it to the `notifications` collection in the database.
        2.  Use the `ConnectionManager` to check if the recipient is currently online.
        3.  If they are online, it will push the new notification to them instantly via their active WebSocket connection.

### Phase 2.4: REST API Endpoints for Notifications
1.  **Update `app/routers/notifications.py`:**
    *   The standard REST API endpoints remain crucial for managing notifications when a user is not connected via WebSocket.
    *   `GET /notifications/`: Retrieves all of a user's notifications (both read and unread) from the database. This is essential for loading history or for clients that do not use WebSockets.
    *   `PATCH /notifications/{notification_id}/read`: Allows a user to mark a specific notification as read.

### Phase 2.5: Integration with Application Logic
1.  **Modify `app/routers/appointments.py`:**
    *   The `create_and_send_notification` utility will be called at key events:
        *   When a patient requests an appointment, a notification will be sent to the specialist.
        *   When a specialist confirms an appointment, a notification will be sent to the patient.
        *   When an appointment is cancelled (Note: a `cancel_appointment` endpoint will need to be added), a notification will be sent to the other party.
